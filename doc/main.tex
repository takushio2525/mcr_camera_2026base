\section{概要}\label{sec:overview}

GR-PEACH (RZ/A1H) を使用した、マイコンカーラリー (MCR) カメラクラス開発のためのベースプログラムである。

\begin{notebox}[設計思想]
\begin{itemize}[nosep]
  \item mbed OS を使用せず、ルネサス標準の \texttt{iodefine.h} を用いたベアメタル（レジスタ直接操作）環境で構築する
  \item 既存のスパゲッティコードを廃し、EMA (Embedded-Module-Architecture) 準拠のモジュール分割を採用する。
        全モジュールは共通インターフェース \texttt{IModule} を実装し、
        \texttt{init()} / \texttt{updateInput()} / \texttt{updateOutput()} の3点で統一的に扱う
  \item モジュール間のデータ受け渡しは共有構造体 \texttt{SystemData} に一本化し、
        モジュールが他モジュールのメソッドを直接呼ぶことを禁止する
  \item 調整対象の定数は \texttt{src/core/ProjectConfig.h} に集約し、
        「走行調整のためにドライバのソースを触る」状況をなくす
\end{itemize}
\end{notebox}

\subsection{用語定義}

\begin{tabularx}{\textwidth}{l X}

\section{背景・課題}\label{sec:background}

\subsection{本プログラムに至る経緯}\label{sec:lineage}

本プログラムは、公式配布のサンプルプログラムをそのまま使い続けられなくなったことを
直接の契機として、ゼロから作り直したものである。経緯は次の3段階になる。

\begin{tabularx}{\textwidth}{l l l X}
\toprule
\textbf{プロジェクト} & \textbf{開発環境} & \textbf{mbed OS} & \textbf{位置づけ} \\
\midrule
\texttt{kit20\_gr-peach} & e2 studio & あり & 画像処理マイコンカーキットの公式配布プログラム \\
\texttt{MCR\_SHIOZAWA\_CCLASS} & mbed Studio & あり & 上記を出発点に自作した走行プログラム（最高 2.38\,m/s） \\
\textbf{本プログラム} & e2 studio & \textbf{なし} & mbed OS を排したベアメタル実装。本仕様書の対象 \\
\bottomrule
\end{tabularx}

\vspace{2mm}
公式配布版も本プログラムも同じ e2 studio を使うため、
\textbf{本移行は統合開発環境の乗り換えではない}。
実際に変えたのは \textbf{mbed OS への依存を断ったこと}である。

\begin{cautionbox}[開発環境の課題]
\begin{enumerate}[nosep]
  \item \textbf{公式配布版が現行 e2 studio でビルドできない}:
        公式配布版の \texttt{.cproject} は、ビルド設定の識別子が
        \texttt{ilg.gnuarmeclipse.managedbuild.cross.*}
        （サードパーティ製プラグイン GNU ARM Eclipse、後の Eclipse Embedded CDT）
        の名前空間で記述されている。現行の e2 studio が使う
        \texttt{com.renesas.cdt.managedbuild.gcc.rz.*} とは名前空間ごと非互換であり、
        個別のコンパイルエラーを解消する作業ではなく
        \textbf{ビルド定義そのものが解釈できない}。
        設定値（Cortex-A9 / ARMv7-A / VFPv3 / hard float ABI）自体は現行環境でも
        指定可能なものばかりで、\textbf{問題は設定値ではなく設定を記述する枠組みにある}
  \item \textbf{mbed OS サービス終了}: mbed のサービス終了に伴い、将来的な継続利用や保守が困難になる。
        公式配布版は mbed OS 本体 692 ファイル・mbed-gr-libs 423 ファイルを同梱しており、
        利用者が記述するコードは 1 ファイル（約 1,700 行）のみで、
        残りは供給元が終了した土台に載っている
  \item \textbf{ブラックボックス化の解消}: OS内部処理への依存を減らし、デバッグを容易にする必要がある
\end{enumerate}
\end{cautionbox}

\begin{notebox}[公式配布物の扱い]
本仕様書は公式配布物（プログラム本体および解説マニュアル）の内容を転載していない。
いずれも文書による事前の承諾なしの転載・複製が禁じられているため、
参照はファイル名・関数名・設定識別子にとどめている。
本プログラムのソースコードに公式配布版から複製したコードは含まれない。
\end{notebox}

\section{システムアーキテクチャ}\label{sec:architecture}

システムは OSTM0 による 1ms 周期のタイマー割り込みで同期して動作する。
割り込みハンドラ \texttt{ostm0\_interrupt\_callback()} が
Input $\rightarrow$ Logic $\rightarrow$ Output の3フェーズを毎周期実行し、
メインループはフレーム完了待ち・ライン検出・ログ処理・デバッグ表示を担当する。

Input / Output の各フェーズは \texttt{IModule*} の配列 (\texttt{s\_inputModules[]} /
\texttt{s\_outputModules[]}) をループして呼び出す。
モジュールの \texttt{enabled} が \texttt{false} の間はスキップされるため、
初期化に失敗したモジュールを配列から外さずに無効化できる。
この \texttt{enabled} は \texttt{main()} が \texttt{initModule()}
(\hyperref[sec:api-moduleinit]{§\ref*{sec:api-moduleinit}}) 経由で初期化を行った時点で確定する。

\begin{lstlisting}[caption={Input / Output フェーズの配列駆動 (mcr\_camera\_2026base.cpp)},label=lst:phasearray]
static IModule* s_inputModules[] = {
    &g_onboard,   // Input : SW 状態を sys.ob.sw へ
    &g_camera,    // Input : 1ms ごとのフレーム段階処理
};
static IModule* s_outputModules[] = {
    &g_motor,     // Output : sys.mot.*Cmd  -> PWM
    &g_servo,     // Output : sys.srv.angleCmd -> PWM
    &g_onboard,   // Output : sys.ob.*LedCmd  -> GPIO
};

for (int i = 0; i < N_IN; ++i) {
    if (s_inputModules[i]->enabled) s_inputModules[i]->updateInput(g_sys);
}
\end{lstlisting}

\subsection{3フェーズモデル}\label{sec:threephase}

\begin{tabularx}{\textwidth}{c l X}
\toprule
\textbf{順序} & \textbf{フェーズ} & \textbf{内容} \\
\midrule
1 & Input  & ハードウェア $\rightarrow$ \texttt{SystemData}。各モジュールの
             \texttt{updateInput(sys)} がセンサ値を \texttt{sys.*} へ書き込む \\
2 & Logic  & \texttt{SystemData} $\rightarrow$ \texttt{SystemData}。
             \texttt{applyDrivingPattern(sys)} が状態機械を進め、
             出力指示を \texttt{sys.mot.*Cmd} / \texttt{sys.srv.angleCmd} /
             \texttt{sys.ob.*LedCmd} へ\textbf{代入する}（\textbf{ドライバは呼ばない}） \\
3 & Output & \texttt{SystemData} $\rightarrow$ ハードウェア。各モジュールの
             \texttt{updateOutput(sys)} が \texttt{*Cmd} を読み、レジスタへ反映する \\
\bottomrule
\end{tabularx}

\begin{notebox}[3フェーズ分離の利点]
Logic フェーズはハードウェアに一切触れない純粋な計算になるため、
\texttt{SystemData} を差し替えるだけで PC 上の単体テストに載せられる。
また出力タイミングが Output フェーズに集約されるので、
1ms 内で出力が二度書きされたり、Logic の途中経過が物理出力に漏れることがない。
\end{notebox}

\begin{cautionbox}[全モジュールがラッチ方式ではない]
Output フェーズ内での反映方法はモジュールによって異なる。
\texttt{Onboard} は4個の LED 状態を内部バッファ \texttt{ledState\_[]} にまとめてから
GPIO へ一括書き込みする真のラッチ方式だが、
\texttt{Motor} / \texttt{Servo} は \texttt{updateOutput()} 内で MTU2 レジスタへ直接書き込む。
いずれも「Output フェーズでのみ書く」点は共通であり、
Logic フェーズの途中経過が出力に漏れない性質は保たれている。
\end{cautionbox}

\subsection{共有データ構造 SystemData}\label{sec:systemdata}

\texttt{SystemData}（\texttt{src/core/SystemData.h}）は全モジュールの入出力データを
1つに集約した構造体である。実体はグローバル変数 \texttt{g\_sys}
（\texttt{mcr\_camera\_2026base.cpp} で定義）1個のみで、
3フェーズの全呼び出しがこの参照を受け取る。

\begin{lstlisting}[caption={SystemData の定義},label=lst:systemdata]
struct SystemData {
    CameraData       cam;   // Camera       が所有
    LineDetectorData line;  // LineDetector が所有
    MotorData        mot;   // Motor        が所有
    ServoData        srv;   // Servo        が所有
    OnboardData      ob;    // Onboard      が所有
    EncoderData      enc;   // Encoder      が所有
    SerialData       ser;   // Serial       が所有
    SDLoggerData     sd;    // SDLogger     が所有
    RunData          run;   // RunLogic     が所有
};
extern SystemData g_sys;
\end{lstlisting}

\begin{tabularx}{\textwidth}{l l X}
\toprule
\textbf{メンバ} & \textbf{型} & \textbf{主な内容} \\
\midrule
\texttt{cam}  & \texttt{CameraData}       & \texttt{frameReady}, \texttt{frameCount}, \texttt{field}, \texttt{imageBufferPtr} \\
\texttt{line} & \texttt{LineDetectorData} & \texttt{deviation[120]}, \texttt{crossLine}, \texttt{leftLine}, \texttt{rightLine}, \texttt{centerLine}, \texttt{sensorBin} \\
\texttt{mot}  & \texttt{MotorData}        & \texttt{leftCmd}, \texttt{rightCmd}, \texttt{leftActual}, \texttt{rightActual} \\
\texttt{srv}  & \texttt{ServoData}        & \texttt{angleCmd}, \texttt{angleActual} \\
\texttt{ob}   & \texttt{OnboardData}      & \texttt{sw}, \texttt{ledRedCmd}, \texttt{ledGreenCmd}, \texttt{ledBlueCmd}, \texttt{userLedCmd} \\
\texttt{enc}  & \texttt{EncoderData}      & \texttt{totalCount}, \texttt{magaCount}, \texttt{cnt}, \texttt{avgCnt}, \texttt{filteredCnt} \\
\texttt{ser}  & \texttt{SerialData}       & \texttt{txCount} \\
\texttt{sd}   & \texttt{SDLoggerData}     & \texttt{ready}, \texttt{logCount}, \texttt{full}, \texttt{saveRequested}, \texttt{saveDone} \\
\texttt{run}  & \texttt{RunData}          & \texttt{pattern}, \texttt{handleVal}, \texttt{finished}, 3本の \texttt{ModuleTimer} \\
\bottomrule
\end{tabularx}

\begin{notebox}[データの所有権]
\texttt{\{Module\}Data} 構造体の宣言は各モジュールのヘッダ側に置き、
\texttt{SystemData.h} はそれを include して集約するだけである。
各モジュールは原則として\textbf{自身の Data だけ}を読み書きし、
他モジュールのデータを横断参照してよいのは Logic フェーズの関数だけ、というルールで運用する。
\end{notebox}

\begin{notebox}[Camera だけは宣言ヘッダを分離している]
\texttt{SystemData.h} が include するのは
\texttt{Camera.h} ではなく \texttt{src/drivers/CameraData.h} である
（他の8モジュールは \texttt{Motor.h} 等のドライバヘッダをそのまま include する）。

\texttt{Camera.h} は VDC5 ドライバ (\texttt{video/DisplayBace.h} $\rightarrow$
\texttt{pinmap.h}) を include し、その先で実機のレジスタ定義
(\texttt{iodefine.h} の \texttt{INTC}) を要求する。
一方 \texttt{SystemData.h} が Camera から必要としているのは \texttt{CameraData} 型だけで、
VDC5 の API は一切要らない。にもかかわらず \texttt{SystemData.h} が
\texttt{Camera.h} を include していたため、
\texttt{SystemData.h} を使う全モジュール（Motor / Servo / Encoder 等）が
\textbf{VDC5 ドライバ一式に依存}してしまい、
モータ1個のホスト側テストにカメラ HAL 全部が必要になっていた。
これが \texttt{tests/} をビルド不能にしていた直接の原因である。

そこでハードウェア非依存の宣言（\texttt{CameraConfig} / \texttt{CameraData} /
\texttt{CAM\_*} マクロ）だけを \texttt{CameraData.h} へ移し、
\texttt{DisplayBase} を持つ \texttt{Camera} クラス本体は \texttt{Camera.h} に残した。
\texttt{Camera.h} は \texttt{CameraData.h} を include するため、
\texttt{Camera.h} を include する側から見える宣言の集合は分離前と同一であり、
「Data の所有権はモジュール側にある」というルールも維持されている。
\end{notebox}

\begin{cautionbox}[画素バッファは SystemData に置かない]
160$\times$120 の輝度バッファ（約 19KB）と YCbCr422 中間バッファ（約 38KB）は
\texttt{Camera} クラス内に実体を持ち、\texttt{SystemData} からは
\texttt{cam.imageBufferPtr} 経由で参照する。
巨大な配列を \texttt{SystemData} に持たせるとメモリ効率とコピーコストが悪化するため。
\end{cautionbox}

\subsection{ModuleTimer --- ノンブロッキング時間計測}\label{sec:moduletimer}

ベアメタル環境には Arduino の \texttt{millis()} に相当する API がないため、
OSTM0 の 1ms 割り込みでインクリメントされるグローバルカウンタ
\texttt{volatile unsigned long g\_timer\_1ms} を時刻源とする軽量クラスを用意している
（\texttt{src/core/ModuleTimer.h}）。

\begin{tabularx}{\textwidth}{l X}
\toprule
\textbf{メソッド} & \textbf{機能} \\
\midrule
\texttt{void setTime()}                    & 現在時刻を起点としてタイマーを開始する \\
\texttt{unsigned long getNowTime() const}  & \texttt{setTime()} からの経過時間 [ms]。未起動なら 0 \\
\texttt{bool isExpired(unsigned long ms) const} & 指定時間以上経過したか。未起動なら \texttt{false} \\
\texttt{void reset()}                      & 停止状態に戻す \\
\texttt{bool isRunning() const}            & 起動中かどうか \\
\bottomrule
\end{tabularx}

\vspace{2mm}
\texttt{RunData} はこれを3本保持し、旧実装のカウンタ変数を置き換えている
(\hyperref[sec:api-runlogic]{§\ref*{sec:api-runlogic}})。

\begin{notebox}[待ちループを書かないこと]
\texttt{ModuleTimer} は「経過したか」を問い合わせるだけで、内部でブロックしない。
1ms 割り込みの中で \texttt{while (!timer.isExpired(n))} のような待機を書くと
\texttt{g\_timer\_1ms} が進まなくなり、確実にハングする。
\end{notebox}

\subsection{設定注入と ProjectConfig}\label{sec:configinject}

各モジュールは \texttt{\{Module\}Config} 構造体を\textbf{コンストラクタ引数で受け取り}、
内部に \texttt{\_config} としてコピーして保持する。
実値の定義は \texttt{src/core/ProjectConfig.h} の1ファイルに集約されており、
走行パラメータの調整でドライバのソースを編集する必要はない。

\begin{lstlisting}[caption={Config 注入によるインスタンス生成 (mcr\_camera\_2026base.cpp)},label=lst:configinject]
Serial       g_serial      (SERIAL_CONFIG);
Onboard      g_onboard     (ONBOARD_CONFIG);
Motor        g_motor       (MOTOR_CONFIG);
Servo        g_servo       (SERVO_CONFIG);
Encoder      g_encoder     (ENCODER_CONFIG);   // 現状 init/呼出は未接続
Camera       g_camera      (CAMERA_CONFIG);
LineDetector g_lineDetector(LINE_DETECTOR_CONFIG);
SDCard       g_sdcard      (SDCARD_CONFIG);
SDLogger     g_sdlogger    (SDLOGGER_CONFIG);
\end{lstlisting}

実際の設定値は \hyperref[sec:params]{§\ref*{sec:params}}「パラメータ調整ガイド」にまとめる。

\begin{cautionbox}[Config はグローバル ctor に依存する]
\texttt{\_config} メンバはコンストラクタ初期化で埋まる。
本プロジェクトの \texttt{start.S} は \texttt{\_\_libc\_init\_array()} を呼ばないため、
\texttt{main()} 冒頭の \texttt{runGlobalConstructors()} を経由しないと
\texttt{\_config} が BSS のゼロのままになり、サーボ出力が 0 になる等の致命的な不具合になる。
詳細は \hyperref[sec:ctors]{§\ref*{sec:ctors}} を参照。
\end{cautionbox}

\section{API仕様}\label{sec:api}

本章では各モジュールの公開APIをデータシート形式で記述する。

%% ── 7.1 IModule ──
\subsection{IModule インターフェース}\label{sec:api-imodule}

\begin{apibox}{IModule --- 基底インターフェース}

\textbf{ファイル:} \texttt{src/core/IModule.h} \hfill
\textbf{種別:} 純粋仮想クラス

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

全てのドライバが実装する共通インターフェース。
3フェーズ実行モデル (\hyperref[sec:threephase]{§\ref*{sec:threephase}}) に対応し、
入力と出力を別メソッドに分けている点が特徴である。

\begin{itemize}[nosep]
  \item 入力専用モジュール（Camera, Encoder）は \texttt{updateInput()} のみを override する
  \item 出力専用モジュール（Motor, Servo, Serial, SDCard, SDLogger）は \texttt{updateOutput()} のみを override する
  \item 入出力両方のモジュール（Onboard）は両方を override する
\end{itemize}

\texttt{SystemData} は前方宣言のみを行い、各モジュールヘッダから
\texttt{SystemData.h} を include させないことで循環依存を避けている。

\apisection{関数ドキュメント}

\begin{funcblock}{init()}
\texttt{virtual bool init() = 0}

\vspace{1.5mm}
初期化処理。レジスタ設定・変数初期化を行う。システム起動時に \texttt{main()} から1回のみ呼び出される。

\vspace{1.5mm}
\textbf{戻り値:} \texttt{bool} --- \texttt{true}=成功 / \texttt{false}=失敗。
失敗時は呼び出し側で \texttt{enabled = false} に落とす。
この判定は \texttt{main()} が直接書くのではなく
\texttt{initModule()} (\hyperref[sec:api-moduleinit]{§\ref*{sec:api-moduleinit}})
が一手に引き受ける。
\end{funcblock}

\begin{funcblock}{updateInput(sys)}
\texttt{virtual void updateInput(SystemData\& sys)}

\vspace{1.5mm}
入力フェーズ。ハードウェアを読み取り、結果を \texttt{sys} の自モジュール領域へ書き込む。
デフォルトは空実装のため、出力専用モジュールは override 不要。
\end{funcblock}

\begin{funcblock}{updateOutput(sys)}
\texttt{virtual void updateOutput(SystemData\& sys)}

\vspace{1.5mm}
出力フェーズ。\texttt{sys} の指示値（\texttt{*Cmd}）を読み、ハードウェアへ反映する。
デフォルトは空実装のため、入力専用モジュールは override 不要。
\end{funcblock}

\begin{funcblock}{deinit()}
\texttt{virtual void deinit()}

\vspace{1.5mm}
終了処理（バス停止、リソース解放等）。デフォルトは何もしない。
\end{funcblock}

\apisection{メンバ変数}

\begin{tabularx}{\textwidth}{l l l X}
\toprule
\textbf{変数名} & \textbf{型} & \textbf{初期値} & \textbf{説明} \\
\midrule
\texttt{enabled} & \texttt{bool} & \texttt{true} &
  \texttt{false} の間は呼び出し側の配列ループが
  \texttt{updateInput}/\texttt{updateOutput} をスキップする \\
\bottomrule
\end{tabularx}

\apisection{インターフェース定義}

\begin{lstlisting}[caption={IModule インターフェース定義},label=lst:imodule]
struct SystemData;   // 前方宣言（循環依存の回避）

class IModule {
public:
  virtual ~IModule() {}

  // 初期化処理（成功 = true、失敗 = false）
  virtual bool init() = 0;

  // 入力フェーズ: ハードウェア -> SystemData
  virtual void updateInput(SystemData& sys) { (void)sys; }

  // 出力フェーズ: SystemData -> ハードウェア
  virtual void updateOutput(SystemData& sys) { (void)sys; }

  // 終了処理（バス停止、リソース解放等）
  virtual void deinit() {}

  // false の間は updateInput / updateOutput をスキップする
  bool enabled = true;
};
\end{lstlisting}

\apisection{新規モジュールの追加手順}

\begin{enumerate}[nosep, leftmargin=*]
  \item \texttt{src/drivers/Xxx.h} に \texttt{XxxConfig} と \texttt{XxxData} を宣言する
  \item \texttt{class Xxx : public IModule} を定義し、\texttt{explicit Xxx(const XxxConfig\&)} を用意する
  \item \texttt{SystemData.h} に \texttt{XxxData xxx;} を追加し、ヘッダを include する
  \item \texttt{ProjectConfig.h} に \texttt{XXX\_CONFIG} の実値を定義する
  \item \texttt{mcr\_camera\_2026base.cpp} でグローバルインスタンス \texttt{g\_xxx} を生成し、
        \texttt{main()} で \texttt{initModule(g\_xxx)}（実際には \texttt{initAndReport()}）
        を呼び、必要なフェーズの配列へ登録する。
        \texttt{init()} を直接呼ぶと \texttt{enabled} が更新されず、
        失敗しても無効化されないので注意する
\end{enumerate}

\end{apibox}

%% ── 7.2 ModuleInit ──
\subsection{initModule --- 初期化の戻り値契約}\label{sec:api-moduleinit}

\begin{apibox}{ModuleInit.h --- init() の戻り値を enabled へ反映するヘルパ}

\textbf{ファイル:} \texttt{src/core/ModuleInit.h} \hfill
\textbf{種別:} インライン自由関数（ヘッダのみ）

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

\texttt{IModule} は「\texttt{init()} が \texttt{false} を返したら呼び出し側で
\texttt{enabled = false} に落とす」という運用を前提に設計されている
(\hyperref[sec:api-imodule]{§\ref*{sec:api-imodule}})。
\texttt{initModule()} はその契約を実装する唯一の関数である。

契約を1箇所に閉じ込めたのは、判定を各呼び出し箇所に手書きすると必ず書き忘れが出るためである。
実際、本ヘッダの導入前は \texttt{main()} が\textbf{全ての \texttt{init()} の戻り値を捨てており}、
\texttt{enabled} に \texttt{false} を書く箇所が一つも存在しなかった。
その結果、SD 未挿入で \texttt{SDLogger::init()} が失敗しても
\texttt{updateOutput()} が毎周期呼ばれ続けて空振りしていた。

\apisection{定義}

\begin{lstlisting}[caption={initModule() の定義 (core/ModuleInit.h)},label=lst:moduleinit]
inline bool initModule(IModule& mod)
{
    const bool ok = mod.init();
    mod.enabled   = ok;
    return ok;
}
\end{lstlisting}

\apisection{関数ドキュメント}

\begin{funcblock}{initModule(mod)}
\texttt{inline bool initModule(IModule\& mod)}

\vspace{1.5mm}
\texttt{mod.init()} を1回だけ呼び、その結果をそのまま \texttt{mod.enabled} へ反映する。

\vspace{1.5mm}
\textbf{引数:} \texttt{mod} --- 初期化対象のモジュール\quad
\textbf{戻り値:} \texttt{bool} --- \texttt{init()} の結果そのもの。
呼び出し側はこれを見てシリアル出力等の障害報告を行う
(\hyperref[sec:bootseq]{§\ref*{sec:bootseq}})
\end{funcblock}

\apisection{失敗したモジュールの扱い}

\texttt{enabled = false} になったモジュールは、以後3フェーズ実行から外れる。
判定箇所は2種類ある。

\begin{tabularx}{\textwidth}{l X}
\toprule
\textbf{対象} & \textbf{スキップの判定箇所} \\
\midrule
ISR 配列に載るモジュール &
  \texttt{ostm0\_interrupt\_callback()} の \texttt{s\_inputModules[]} /
  \texttt{s\_outputModules[]} ループ (\hyperref[sec:isr]{§\ref*{sec:isr}}) \\
配列外の \texttt{LineDetector} / \texttt{SDLogger} &
  \texttt{runMainLoop()} / \texttt{runDebugLoop()} 側の呼び出し
  (\hyperref[sec:mainloop]{§\ref*{sec:mainloop}}) \\
\bottomrule
\end{tabularx}

\begin{notebox}[現時点で false を返しうるのは2モジュールだけ]
\texttt{Camera::init()}（VDC5 / DVDEC の各初期化ステップ）と
\texttt{SDLogger::init()}（SD 未挿入・FatFs マウント失敗）のみが \texttt{false} を返す。
\texttt{Onboard} / \texttt{Serial} / \texttt{Motor} / \texttt{Servo} /
\texttt{LineDetector} / \texttt{Encoder} は現状レジスタ設定と変数初期化だけなので
無条件に \texttt{true} を返す。
契約自体は全モジュールに適用されているため、
将来これらに失敗経路を足しても \texttt{main()} 側の変更は要らない。
\end{notebox}

\begin{notebox}[ホスト側テストで検証できる]
\texttt{initModule()} はハードウェアに一切触れないため、
PC 上の単体テスト \texttt{tests/test\_module\_contract.cpp} から直接検証できる。
「\texttt{init()} が \texttt{false} なら \texttt{enabled} が落ちる」
「\texttt{enabled = false} のモジュールは3フェーズ実行から外れる」の2点を
フェイクモジュールで確認している。
\end{notebox}

\end{apibox}

%% ── 7.3 Encoder ──
\subsection{Encoder クラス}\label{sec:api-encoder}

\begin{apibox}{Encoder --- エンコーダドライバ}

\textbf{ファイル:} \texttt{src/drivers/Encoder.h}, \texttt{Encoder.cpp} \hfill
\textbf{継承:} \texttt{IModule} \hfill
\phasebadge{Input フェーズ}

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

MTU2 チャネル1の位相計数モード2を使用し、エンコーダのパルスをカウントする。
1ms ごとに \texttt{MTU2TCNT\_1} を読んでゼロクリアし、
その差分（1ms あたりのパルス数）を累積カウンタと2種類のフィルタに通す。

\begin{cautionbox}[現状 ISR に未接続]
\texttt{g\_encoder} のインスタンス自体は生成されているが、
\texttt{main()} での \texttt{init()} 呼び出しと \texttt{s\_inputModules[]} への登録は
まだ行われていない。したがって \texttt{sys.enc.*} は常に 0 のままである。
SDLogger 連携が必要になった時点で有効化する予定。
\end{cautionbox}

\apisection{機能一覧}

\begin{itemize}[nosep]
  \item MTU2 位相計数モード2による前進/後退を区別したパルス計数
  \item 走行距離換算用の累積カウント（\texttt{totalCount}）とクランク検出用（\texttt{magaCount}）の2系統
  \item 移動平均フィルタ（段数 \texttt{filterN}）
  \item RC フィルタ（指数移動平均、係数 \texttt{rcAlpha}）
\end{itemize}

\apisection{設定 (EncoderConfig)}

\begin{tabularx}{\textwidth}{l l l X}
\toprule
\textbf{メンバ} & \textbf{型} & \textbf{実値} & \textbf{説明} \\
\midrule
\texttt{filterN}  & \texttt{int}   & 4    & 移動平均の段数（上限は \texttt{Encoder::FILTER\_N = 4}） \\
\texttt{rcAlpha}  & \texttt{float} & 0.5  & RC フィルタ係数 $\alpha$ \\
\texttt{aPinFmt}  & \texttt{int}   & 0    & A相 P1\_0 (TCLKA) \\
\texttt{bPinFmt}  & \texttt{int}   & 10   & B相 P1\_10 (TCLKB) \\
\bottomrule
\end{tabularx}

\apisection{出力データ (EncoderData / sys.enc)}

\begin{tabularx}{\textwidth}{l l X}
\toprule
\textbf{メンバ} & \textbf{型} & \textbf{説明} \\
\midrule
\texttt{totalCount}  & \texttt{int}   & 走行距離換算用の累積カウント \\
\texttt{magaCount}   & \texttt{int}   & クランク検出用の累積カウント \\
\texttt{cnt}         & \texttt{int}   & 直近 1ms あたりのカウント（符号付き） \\
\texttt{avgCnt}      & \texttt{int}   & 移動平均後のカウント \\
\texttt{filteredCnt} & \texttt{float} & RC フィルタ後のカウント \\
\bottomrule
\end{tabularx}

\begin{notebox}[距離ではなくパルス数を扱う]
本実装が保持しているのは\textbf{パルスカウント（\texttt{int}）}であり、
距離 [mm] や速度への換算は行っていない。
走行状態の遷移条件は経過時間 [ms] で管理する方針
(\hyperref[sec:api-runlogic]{§\ref*{sec:api-runlogic}}) のため、
距離換算係数（1パルスあたりの移動距離）は定義していない。
\end{notebox}

\apisection{関数ドキュメント}

\begin{funcblock}{init()}
\texttt{bool init() override}

\vspace{1.5mm}
MTU2 チャネル1を位相計数モード2で初期化する。
P1\_0 / P1\_10 のピン設定、MTU2 のスタンバイ解除、カウンタスタートを行う。
\end{funcblock}

\begin{funcblock}{updateInput(sys)}
\texttt{void updateInput(SystemData\& sys) override}

\vspace{1.5mm}
\texttt{MTU2TCNT\_1} を符号付き 16bit として読み出して 0 にリセットし、
累積カウンタ・移動平均・RC フィルタを更新して \texttt{sys.enc.*} に格納する。
RC フィルタは $\mathit{rc} \leftarrow \alpha \cdot \mathit{rc} + (1-\alpha) \cdot \mathit{cnt}$ で更新する。
\end{funcblock}

\begin{funcblock}{clearTotal() / clearMaga()}
\texttt{void clearTotal()} / \texttt{void clearMaga()}

\vspace{1.5mm}
それぞれ \texttt{totalCount\_} / \texttt{magaCount\_} を 0 にリセットする。
\end{funcblock}

\begin{funcblock}{後方互換 getter}
\texttt{int getTotalCount() const} / \texttt{int getMagaCount() const} /
\texttt{int getCnt() const} / \texttt{float getFilteredCnt() const}

\vspace{1.5mm}
内部状態を直接返す。\texttt{getCnt()} は移動平均後の値（\texttt{avg\_}）を返す点に注意。
新規コードでは \texttt{sys.enc.*} を読むこと。
\end{funcblock}

\apisection{ハードウェアマッピング}

\begin{tabularx}{\textwidth}{l l l X}
\toprule
\textbf{信号} & \textbf{ピン} & \textbf{レジスタ} & \textbf{説明} \\
\midrule
A相 & P1\_0  (TCLKA) & MTU2TCNT\_1 & 位相計数モード2の入力 \\
B相 & P1\_10 (TCLKB) & MTU2TCNT\_1 & 同上（位相差で方向を判別） \\
\bottomrule
\end{tabularx}

\end{apibox}

\subsection{Camera クラス}\label{sec:api-camera}

\begin{apibox}{Camera --- NTSC ビデオキャプチャドライバ}

\textbf{ファイル:} \texttt{src/drivers/Camera.h}, \texttt{Camera.cpp},
\texttt{CameraData.h} \hfill
\textbf{継承:} \texttt{IModule} \hfill
\phasebadge{Input フェーズ}

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

VDC5 チャネル0 と DVDEC0 を用いて NTSC 映像を 160$\times$120 の YCbCr422 として取り込み、
輝度（Y）成分のみを抽出して 160$\times$120 のグレースケールバッファに格納する。
初期化には \texttt{mbed-gr-libs} 由来の \texttt{DisplayBase} API
（\texttt{Graphics\_init} $\rightarrow$ \texttt{Graphics\_Video\_init} $\rightarrow$
\texttt{Video\_Write\_Setting}）を使用する。

\apisection{機能一覧}

\apisection{フレーム処理の4ステップ分割}

XIP 実行環境では \texttt{imageCopy()} 1回に約 7--8ms を要し、1ms 割り込みに収まらない
(\hyperref[sec:xip]{§\ref*{sec:xip}})。そのため1フレームの処理を4ステップに分割し、
1ms 割り込みごとに1ステップだけ進める。

\begin{tabularx}{\textwidth}{c l X}
\toprule
\textbf{ステップ} & \textbf{処理} & \textbf{内容} \\
\midrule
0 & \texttt{imageCopy(0)}         & Vfield 値を \texttt{capturedField\_} にキャプチャし、前半（0--59行）をコピー \\
1 & \texttt{imageCopy(1)}         & 後半（60--119行）をコピー \\
2 & \texttt{extractBrightness(0)} & 前半の Y 成分を抽出 \\
3 & \texttt{extractBrightness(1)} & 後半の Y 成分を抽出。完了時に \texttt{frameReady\_} を立てる \\
4以降 & Vfield 待ち              & 次の Vfield 発生まで即リターンし、メインループへ CPU 時間を返す \\
\bottomrule
\end{tabularx}

\begin{notebox}[capturedField\_ 方式が必要な理由]
XIP 環境では4ステップの合計が NTSC の Vfield 間隔（16.7ms）を超えるため、
\texttt{imageCopy()} と \texttt{extractBrightness()} がそれぞれ Vfield トグルを読み直すと
\textbf{異なるフィールド値を使ってしまい画像が乱れる}。
ステップ0で1回だけ値を確保し、4ステップ全体で同じ値を使うことでこれを防いでいる。
また、フレーム処理中（ステップ0--3）は Vfield 変化を無視する。
処理中にリセットを掛けるとステップ1以降へ進めず、輝度バッファが永久に更新されない。
\end{notebox}

\end{notebox}

\textbf{部分的に設定された VDC5 がその後どう振る舞うかは未確認}である。
従来は同じ箇所で無限ループしていたため、この経路を通した実績が無い。
登録済みの割り込みコールバックだけが残る、キャプチャが停止しないまま残る、

\end{cautionbox}

\subsection{LineDetector クラス}\label{sec:api-linedetector}

\begin{apibox}{LineDetector --- ライン検出モジュール}

\textbf{ファイル:} \texttt{src/drivers/LineDetector.h}, \texttt{LineDetector.cpp} \hfill
\textbf{継承:} \texttt{IModule} \hfill
\phasebadge{Input フェーズ（メインループ実行）}

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

\texttt{Camera} が生成した輝度バッファからコースの白線を検出し、
各行の偏差・各種ラインフラグ・8点センサ値を \texttt{sys.line.*} に格納する。
PID 制御は行わず、ハンドル角の算出は \texttt{RunLogic} 側の
\texttt{calcHandle()}（比例ゲイン3段切替）が担当する。

\begin{cautionbox}[ISR ではなくメインループから呼ぶ]
処理が HEIGHT $\times$ WIDTH のループで重いため、1ms 割り込み内では呼ばない。
メインループが \texttt{sys.cam.frameReady == true} を検出したときにのみ
\texttt{g\_lineDetector.updateInput(g\_sys)} を実行する。
このため \texttt{s\_inputModules[]} 配列にも登録されていない。
\end{cautionbox}

\begin{notebox}[g\_camera を直接呼ぶ意図的な例外]
本モジュールは \texttt{sys.cam.imageBufferPtr} を経由せず、
\texttt{g\_camera.getPixel()} と \texttt{g\_camera.thresholdConvert()} を\textbf{直接呼ぶ}。
\hyperref[sec:systemdata]{§\ref*{sec:systemdata}} の
「他モジュールのデータを参照してよいのは Logic フェーズのみ」というルールの例外だが、
1フレームあたり数万回の画素アクセスが発生するため、
性能上の理由で\textbf{意図的にこの経路を採っている}。
\end{notebox}

  \item 全120行分の偏差算出（\texttt{deviation[]}）
  \item クロスライン / 左ハーフライン / 右ハーフライン / センターラインの検出
  \item 8点センサ値（\texttt{sensorBin}）の生成
  \item 走行パターン（\texttt{sys.run.pattern}）に応じた検出パラメータの自動切替

\begin{funcblock}{init()}

\vspace{1.5mm}
\texttt{sys.mot.leftCmd} / \texttt{rightCmd} を内部の \texttt{set()} に渡して PWM へ反映し、
クランプ後の値を \texttt{sys.mot.leftActual} / \texttt{rightActual} に書き戻す。
\end{funcblock}

\begin{funcblock}{getLeft() / getRight()}
\texttt{int getLeft() const} / \texttt{int getRight() const}

\vspace{1.5mm}
内部に保持している現在の出力値を返す（デバッグ用）。
\end{funcblock}

\begin{funcblock}{set(left, right) \normalfont\small\color{gray}[private]}
\texttt{void set(int left, int right)}

\vspace{1.5mm}
両輪の値を \texttt{clamp()} で $[-\mathtt{maxPower}, +\mathtt{maxPower}]$ に丸めてから
\texttt{applyLeft()} / \texttt{applyRight()} を呼ぶ。
\end{funcblock}

\begin{funcblock}{applyLeft(val) / applyRight(val) \normalfont\small\color{gray}[private]}
\texttt{void applyLeft(int val)} / \texttt{void applyRight(int val)}

\vspace{1.5mm}
方向ピンを設定し、デューティ値を MTU2 レジスタへ書き込む。
書き込み先は\textbf{バッファレジスタである \texttt{MTU2TGRC\_4}（左）と
\texttt{MTU2TGRD\_4}（右）のみ}で、\texttt{TGRA\_4} / \texttt{TGRB\_4} は
\texttt{init()} 時の初期化にしか使わない。

\vspace{1.5mm}
デューティ値の計算式:
\[
  \mathit{duty} = \frac{(\mathtt{pwmCycle} - 1) \times |\mathit{val}|}{100}
\]
\end{funcblock}

\apisection{ハードウェアマッピング}

\begin{tabularx}{\textwidth}{l l l X}
\toprule
\textbf{信号} & \textbf{ピン} & \textbf{レジスタ} & \textbf{説明} \\
\midrule
左モータ PWM  & P4\_4 (TIOC4A) & MTU2TGRC\_4 & デューティ（バッファレジスタ） \\
右モータ PWM  & P4\_5 (TIOC4B) & MTU2TGRD\_4 & デューティ（バッファレジスタ） \\
左モータ 方向 & P4\_6 (GPIO)   & GPIO.P4 bit6 & \textbf{High:前進 / Low:後退}（極性反転あり） \\
右モータ 方向 & P4\_7 (GPIO)   & GPIO.P4 bit7 & Low:前進 / High:後退 \\
\bottomrule
\end{tabularx}

\begin{cautionbox}[要実機確認: 左モータの方向ピン極性が左右で非対称]
実装 (\texttt{Motor::applyLeft()}) では左モータのみ方向ピンの極性が反転しており、
\textbf{前進時に P4\_6 を High} にする。右モータ (\texttt{applyRight()}) は
前進時に P4\_7 を Low にする通常の極性である。

ソース上のコメントは「左モーターは配線/ギアの都合で正転=後退となっているため、
ソフト側で方向ピンの極性を反転して補正する」と説明しており、
\textbf{機体側の配線に合わせた意図的な補正}と読める。
ただし本仕様書の旧版は左右とも「Low:正転」と記述しており、記述が食い違っている。

本表は\textbf{現在の実装の実態}を記載したものである。
実機で左右モータの回転方向を実測し、
\textbf{(a)} 配線都合の意図的な補正なのか、
\textbf{(b)} 実装側のバグなのかを確定させること。
実測結果によっては \texttt{Motor.cpp} の修正が必要になる。
\end{cautionbox}

\end{apibox}

\subsection{Servo クラス}\label{sec:api-servo}

\begin{apibox}{Servo --- サーボ PWM ドライバ}

\textbf{ファイル:} \texttt{src/drivers/Servo.h}, \texttt{Servo.cpp} \hfill
\textbf{継承:} \texttt{IModule} \hfill
\phasebadge{Output フェーズ}

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

MTU2 チャネル0 を PWM モード1（分周 P0$\phi$/16、周期約 16ms）で駆動し、
ステアリングサーボの角度を制御する。
出力指示は \texttt{sys.srv.angleCmd} に\textbf{整数の角度 [度]}で与える。

\apisection{機能一覧}

\begin{itemize}[nosep]
  \item MTU2 PWM モード1によるサーボ駆動
  \item 角度 $\rightarrow$ パルス幅カウントの変換
  \item \texttt{maxAngle} による舵角クランプ
  \item 反映後の値を \texttt{sys.srv.angleActual} へ書き戻し
\end{itemize}

\apisection{設定 (ServoConfig)}

\begin{tabularx}{\textwidth}{l l X}
\toprule
\textbf{メンバ} & \textbf{実値} & \textbf{説明} \\
\midrule
\texttt{pwmCycle}   & 33332 & PWM 周期カウント値 \\
\texttt{center}     & 3090  & 中心位置のパルス幅カウント値（約 1.5ms） \\
\texttt{handleStep} & 23    & 1度あたりのカウント値 \\
\texttt{maxAngle}   & 40    & 舵角の絶対値上限 [度] \\
\texttt{pwmPinFmt}  & 0     & P4\_0 (TIOC0A) \\
\bottomrule
\end{tabularx}

\apisection{入出力データ (ServoData / sys.srv)}

\begin{tabularx}{\textwidth}{l l l X}
\toprule
\textbf{メンバ} & \textbf{型} & \textbf{方向} & \textbf{説明} \\
\midrule
\texttt{angleCmd}    & \texttt{int} & Logic $\rightarrow$ Servo & 指示角 $[-40, +40]$ [度] \\
\texttt{angleActual} & \texttt{int} & Servo $\rightarrow$ 外部  & クランプ後に実際に反映した角度 \\
\bottomrule
\end{tabularx}

\apisection{関数ドキュメント}

\begin{funcblock}{init()}
\texttt{bool init() override}

\vspace{1.5mm}
P4\_0 を第2代替機能（TIOC0A）に設定し、MTU2 のスタンバイを解除して
チャネル0 を PWM モード1で起動する。
分周は P0$\phi$/16（\texttt{MTU2TCR\_0 = 0x02}）、バッファ転送は TCNT クリア時
（\texttt{MTU2TBTM\_0 = 0x03}）に設定する。
起動時のパルス幅は \texttt{\_config.center}（中央）である。
\end{funcblock}

\begin{funcblock}{updateOutput(sys)}
\texttt{void updateOutput(SystemData\& sys) override}

\vspace{1.5mm}
\texttt{sys.srv.angleCmd} を内部の \texttt{setAngle()} に渡して PWM へ反映し、
クランプ後の角度を \texttt{sys.srv.angleActual} に書き戻す。
\end{funcblock}

\begin{funcblock}{getAngle()}
\texttt{int getAngle() const}

\vspace{1.5mm}
内部に保持している現在の角度を返す（デバッグ用）。
\end{funcblock}

\begin{funcblock}{setAngle(angle) \normalfont\small\color{gray}[private]}
\texttt{void setAngle(int angle)}

\vspace{1.5mm}
角度をクランプしたうえで、バッファレジスタ \texttt{MTU2TGRD\_0} へ書き込む。
変換式は次のとおりで、\textbf{正の角度でカウント値が減少する}。

\[
  \mathtt{MTU2TGRD\_0} = \mathtt{center} - \mathit{angle} \times \mathtt{handleStep}
\]
\end{funcblock}

\apisection{ハードウェアマッピング}

\begin{tabularx}{\textwidth}{l l l X}
\toprule
\textbf{信号} & \textbf{ピン} & \textbf{レジスタ} & \textbf{説明} \\
\midrule
サーボ PWM & P4\_0 (TIOC0A) & MTU2TGRD\_0 & パルス幅（立ち下がりエッジ、バッファレジスタ） \\
\bottomrule
\end{tabularx}

\begin{cautionbox}[要実機確認: 角度の符号と旋回方向の対応]
実装では正の角度がカウント値の\textbf{減少}に対応する
（\texttt{center - angle * handleStep}）。
\texttt{Servo.h} と \texttt{Servo.cpp} のコメントは
「\texttt{angle}: $-\mathtt{maxAngle}$(右) $\sim$ 0(中央) $\sim +\mathtt{maxAngle}$(左)」
「参考プロジェクト \texttt{handle()} に準拠: 正=左」と記述しており、
\textbf{正の角度で左旋回}という前提である。

一方、本仕様書の旧版は $\mathit{val} = \mathit{angle} \times 23 + \mathtt{CENTER}$
（正の角度でカウント値が増加）と記述しており、\textbf{符号が逆}であった。

本節は\textbf{現在の実装の実態}を記載したものである。
実機でサーボに正の角度を与え、車体が実際にどちらへ切れるかを確認し、
\texttt{RunLogic} のクランク/レーンチェンジのハンドル指示（正=左を前提としている）と
整合しているかを検証すること。
食い違っていた場合は左右のクランクが逆方向に曲がるため、走行が成立しない。
\end{cautionbox}

\end{apibox}

\begin{cautionbox}[要実機確認: ユーザー LED の論理]

実際に点灯するかを確認し、
\textbf{(a)} 旧仕様の記述が誤りだったのか、
\textbf{(b)} 実装に分岐が必要なのかを確定させること。

\apisection{関数ドキュメント}

\begin{funcblock}{init()}
\texttt{bool init() override}

\vspace{1.5mm}
\texttt{STBCR4} の bit5 をクリアして SCIF2 のモジュールストップを解除し、
P6\_3 / P6\_2 を Alt7（TxD2 / RxD2）に設定してから SCIF2 のレジスタを初期化する。
FIFO リセット $\rightarrow$ ボーレート設定 $\rightarrow$ 1ビット時間以上の待機 $\rightarrow$

\texttt{void updateOutput(SystemData\& sys) override}

\end{funcblock}

\texttt{void printf(const char* fmt, ...)}

\vspace{1.5mm}

\end{funcblock}

\texttt{void print(const char* str)}

\vspace{1.5mm}

\vspace{1.5mm}
\textbf{引数:} \texttt{str} (\texttt{const char*}) --- 送信文字列
\end{funcblock}

\begin{funcblock}{putChar(c) \normalfont\small\color{gray}[private]}
\texttt{void putChar(char c)}

\begin{notebox}[ピン選択の根拠]

\subsection{SDCard クラス}\label{sec:api-sdcard}

\begin{apibox}{SDCard --- SD カード SPI ブロックドライバ}

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

\texttt{SDLogger} (\hyperref[sec:api-sdlogger]{§\ref*{sec:api-sdlogger}}) の役割である。

$\rightarrow$ \texttt{diskio.cpp}（ブリッジ）
$\rightarrow$ \texttt{SDCard}（ブロック I/O）
$\rightarrow$ RSPI2（SPI）
\end{notebox}

\apisection{機能一覧}

\begin{itemize}[nosep]
  \item RSPI2 による SPI 通信と CS の手動制御

  \item 複数ブロックの読み書き（\texttt{readBlocks} / \texttt{writeBlocks}）

\apisection{概要}

走行中のデータを RAM 上のリングバッファに蓄積し、

\begin{itemize}[nosep]
  \item 走行中のログ自動記録（パターン番号による記録開始/終了の自動判定）
  \item 4000 エントリ（約 2.7MB）のログバッファ

\end{itemize}

\begin{funcblock}{init()}
\texttt{bool init() override}

\vspace{1.5mm}

成功時に \texttt{mounted\_} を \texttt{true} にする。
\end{funcblock}

\begin{funcblock}{updateOutput(sys)}
\texttt{void updateOutput(SystemData\& sys) override}

\vspace{1.5mm}
次の3つを毎周期実行する。

\begin{enumerate}[nosep, leftmargin=*]
  \item \texttt{sys.sd.ready} / \texttt{logCount} / \texttt{full} を現在値で更新
  \item \texttt{sys.run.pattern} が \texttt{patternMinForLog} 以上かつ

  \item \texttt{sys.sd.saveRequested} が立っていれば \texttt{saveToSD()} を実行し、

\vspace{1.5mm}

\end{funcblock}

\begin{funcblock}{current() / commit()}
\texttt{SDLOG\_T\& current()} / \texttt{void commit()}

\vspace{1.5mm}
\texttt{current()} は次に書き込むエントリへの参照を返し、
\texttt{commit()} が記録番地を1つ進める。

\end{funcblock}

\begin{funcblock}{isReady() / getLogCount() / isFull() / resetLog()}
\texttt{bool isReady() const} / \texttt{unsigned int getLogCount() const} /
\texttt{bool isFull() const} / \texttt{void resetLog()}

\vspace{1.5mm}
マウント状態・記録数・満杯判定の取得と、バッファのリセット。
\end{funcblock}

\begin{lstlisting}[caption={SDLogger の組み込み例（メインループ）},label=lst:sdlogger]

    g_sys.srv.angleCmd = 0;

}

\subsection{RunLogic --- 走行ロジック}\label{sec:api-runlogic}

\begin{apibox}{RunLogic --- 走行状態機械（Logic レイヤー）}

\textbf{ファイル:} \texttt{src/logic/RunLogic.h}, \texttt{RunLogic.cpp} \hfill
\textbf{種別:} \textbf{自由関数の集合（クラスではない）} \hfill
\phasebadge{Logic フェーズ}

\vspace{2mm}\hrule\vspace{2mm}

\apisection{概要}

参考プロジェクト \texttt{mcr\_shiozawa\_cclass\_2.38m-s/main.cpp} の
\texttt{intTimer()} 内 \texttt{switch(pattern)} 状態遷移を移植したもの。
旧設計ではこれを \texttt{RunController} というクラスにしていたが、
EMA 化にあたり\textbf{クラスを廃して純関数 \texttt{applyDrivingPattern()} に分解}し、
インスタンス変数はすべて \texttt{SystemData::run}（\texttt{RunData}）へ移した。

\begin{itemize}[nosep]
  \item 入力: \texttt{sys.line.*}（ライン検出結果）、\texttt{sys.ob.sw}（SW 状態）、\texttt{sys.run.*}（自身の状態）
  \item 出力: \texttt{sys.mot.*Cmd}, \texttt{sys.srv.angleCmd}, \texttt{sys.ob.*LedCmd}, \texttt{sys.run.*}
  \item \textbf{ハードウェアを直接呼ばない}（\texttt{g\_motor} / \texttt{g\_servo} / \texttt{g\_onboard} を参照しない）
  \item 全パラメータは \texttt{RUN\_CONFIG} / \texttt{MOTOR\_CONFIG} から取得する
\end{itemize}

オリジナルは「エンコーダ累積パルス」で距離を管理していたが、
本実装では読みやすさを優先してすべて「経過時間 [ms]」で管理する。
時間管理は \texttt{ModuleTimer} (\hyperref[sec:moduletimer]{§\ref*{sec:moduletimer}}) が担う。

\begin{funcblock}{runLogicInit(sys)}
\texttt{void runLogicInit(SystemData\& sys)}

\vspace{1.5mm}

\texttt{pattern} を \texttt{RP\_WAIT\_SW} に設定して3本の \texttt{ModuleTimer} を起動する。
あわせて初期出力指示（\texttt{sys.mot.*Cmd}, \texttt{sys.srv.angleCmd},
\texttt{sys.ob.*LedCmd}）をすべて 0 にクリアする。
\end{funcblock}

\begin{funcblock}{applyDrivingPattern(sys)}
\texttt{void applyDrivingPattern(SystemData\& sys)}

\vspace{1.5mm}
Logic フェーズで毎周期呼ぶ本体。処理の順序は次のとおり。

\begin{enumerate}[nosep, leftmargin=*]
  \item \texttt{sys.ob.userLedCmd} を中央2点センサ（\texttt{sensorBin \& 0x18}）の反応で更新
  \item \texttt{calcHandle(sys)} でハンドル指示値を算出
  \item \texttt{calcMotorVal(sys)} で通常走行時のモータ値を算出
  \item \texttt{switch (sys.run.pattern)} で29個の \texttt{runXxx()} 関数へ分岐
        （未定義の番号は \texttt{RP\_WAIT\_SW} へ戻す）
  \item \texttt{sys.run.prevPattern} を更新
\end{enumerate}
\end{funcblock}

\apisection{ハンドル指示値の計算}

\texttt{calcHandle()}（\texttt{RunLogic.cpp} 内の static 関数）は
PID ではなく\textbf{比例ゲインの3段切替}でハンドル角を決める。
本プロジェクトで最も頻繁に調整するロジックである。

\vspace{2mm}
$\mathit{dev} = \mathtt{sys.line.deviation[traceRow]}$、
$\mathit{corrected} = \mathit{dev} + \mathtt{sys.run.traceOffset}$ として:

\begin{tabularx}{\textwidth}{l X}
\toprule
\textbf{条件} & \textbf{ハンドル指示値} \\
\midrule
\texttt{pattern < RP\_TRACE\_NORMAL} & 更新しない（停止系のため直前値を維持） \\
\texttt{pattern != RP\_TRACE\_NORMAL} & $\mathit{corrected} \times \mathtt{handleGainNonNormal}$ \\
$|\mathit{dev}| \leq \mathtt{handleStraightAbsThreshold}$ & 0（直線とみなす） \\
$|\mathit{dev}| \leq \mathtt{handleGentleAbsThreshold}$   & $\mathit{corrected} \times \mathtt{handleGainGentle}$（緩カーブ） \\
上記以外 & $\mathit{corrected} \times \mathtt{handleGainSharp}$（急カーブ） \\
\bottomrule
\end{tabularx}

\vspace{2mm}
通常走行時のモータ出力は \texttt{calcMotorVal()} が左右とも
\texttt{MOTOR\_CONFIG.maxPower} に設定する。
ブレーキ時は \texttt{calcBrakeMotorVal()} が \texttt{RUN\_CONFIG.brakeTargetMotor} を用いる。

参考プロジェクト（エンコーダ距離）$\rightarrow$ 本実装（経過時間 ms）の対応:

\midrule
\texttt{encoder.clear()} & \texttt{sys.run.stateTimer.setTime()} & \texttt{changePattern()} が状態遷移時に自動実行 \\

\section{実行モデル詳細}\label{sec:execution}

\subsection{起動シーケンス}\label{sec:bootseq}

\texttt{main()} の初期化順序には\textbf{守らないとハングする制約}が複数ある。
順序を変更する場合は下表の理由を必ず確認すること。
なお各モジュールの初期化は \texttt{init()} の直接呼び出しではなく、
戻り値を \texttt{enabled} へ反映する \texttt{initModule()}
(\hyperref[sec:api-moduleinit]{§\ref*{sec:api-moduleinit}}) 経由で行う。
失敗時の扱いは表の後にまとめる。

\begin{longtable}{c l p{78mm}}
\toprule
\textbf{\#} & \textbf{処理} & \textbf{順序の理由} \\
\midrule
\endfirsthead
\toprule
\textbf{\#} & \textbf{処理} & \textbf{順序の理由} \\
\midrule
\endhead
1  & \texttt{runGlobalConstructors()} & \textbf{最初に実行必須}。\texttt{start.S} が
     \texttt{\_\_libc\_init\_array()} を呼ばないため、これを飛ばすと全モジュールの
     \texttt{\_config} が BSS のゼロのままになる (\hyperref[sec:ctors]{§\ref*{sec:ctors}}) \\
2  & \texttt{SystemInit()}      & FPU / MMU / L1 キャッシュを有効化する。
     この関数の中ではシリアル出力を行わないこと \\
3  & \texttt{initModule(g\_onboard)} & 起動モード判定に \texttt{sw()} を使うため、
     シリアルより先に GPIO を立ち上げる。結果は保持だけして後で報告する \\
4  & \texttt{initModule(g\_serial)}  & 以降の初期化ログを出力するため早期に初期化する。
     ここまでは \texttt{printf} が使えないので、\#3 と本項の結果はまとめて \#5 で報告する \\
5  & 保留した2件の結果報告      & \texttt{g\_onboard} / \texttt{g\_serial} の失敗を
     \texttt{reportInitFailure()} でシリアルと赤 LED へ出す \\
6  & 起動モード判定             & \texttt{g\_onboard.sw()} の結果で
     デバッグモード / 走行モードを決める。カメラ初期化前なので結果をシリアルで確認できる \\
7  & \texttt{initGIC()}         & \textbf{Camera より前に実行必須}。
     VDC5 割り込みの登録が GIC に依存する (\hyperref[sec:gic]{§\ref*{sec:gic}}) \\
8  & \texttt{initAndReport(g\_sdlogger)} & GIC の後・Camera の前。SPI 通信自体に割り込みは不要だが、
     カメラより先に済ませて起動時間を短縮する \\
9  & \texttt{initAndReport(g\_camera)}   & VDC5 / DVDEC を初期化しキャプチャを開始する \\
10 & \texttt{initAndReport(g\_motor)}    & MTU2 ch3/4 のスタンバイ解除と PWM 設定 \\
11 & \texttt{initAndReport(g\_servo)}    & MTU2 ch0 のスタンバイ解除と PWM 設定 \\
12 & \texttt{initAndReport(g\_lineDetector)} & 偏差配列とフラグのクリア \\
13 & \texttt{runLogicInit(g\_sys)}   & \texttt{sys.run.*} と初期出力指示のクリア。
     \texttt{IModule} ではないので \texttt{initModule()} の対象外 \\
14 & 初期化結果のまとめ出力     & 失敗が1件でもあれば警告行を出す。
     起動ログを遡らなくても異常が分かるようにするため \\
15 & \texttt{initOSTM0()}       & \textbf{必ず最後}。下の注意ボックスを参照 \\
16 & 動作モード別ループへ分岐   & \texttt{runDebugLoop()} または \texttt{runMainLoop()} \\
\bottomrule
\end{longtable}

\begin{cautionbox}[initOSTM0() は必ず最後に呼ぶ]
1ms 割り込みが動き出すと、ISR の Output フェーズが\textbf{毎 ms
\texttt{Motor} と \texttt{Servo} を叩く}。
\texttt{g\_motor.init()} / \texttt{g\_servo.init()} より前に OSTM0 を起動すると、
MTU2 がスタンバイ状態のまま PWM レジスタへの書き込みが発生し、
サーボ挙動の異常やバス例外によるハングを招く。

この制約は EMA 化によって「Logic だけでなく Output フェーズも常時実行される」
構造に変わったことで新たに生じたものである。
\end{cautionbox}

\begin{cautionbox}[GIC は Camera より前に初期化する]
逆順にすると、カメラ初期化中に登録された VDC5 のレベルトリガ割り込みが
GIC 無効のため発火せずに蓄積し、後から \texttt{CPSIE i} を実行した瞬間に
一斉発火して\textbf{割り込みストーム}になる。
詳細は \hyperref[sec:gic]{§\ref*{sec:gic}} を参照。
\end{cautionbox}

\subsubsection{初期化失敗時の扱い}\label{sec:bootfail}

初期化が失敗しても\textbf{システムは停止しない}。
\texttt{initModule()} が \texttt{enabled = false} を立てて当該モジュールを
3フェーズ実行から外し、残りのモジュールだけで動作を続ける。
\texttt{main()} は \texttt{initModule()} と障害報告をまとめた
\texttt{initAndReport()} を使う（シリアルがまだ使えない
\texttt{Onboard} / \texttt{Serial} だけは \texttt{initModule()} を直接呼び、報告を後回しにする）。

\begin{lstlisting}[caption={初期化の失敗報告 (mcr\_camera\_2026base.cpp)},label=lst:initreport]
static void reportInitFailure(const char* name)
{
  s_initFailed = true;
  g_serial.printf("\x1b[31m[init] %s の初期化に失敗 → enabled=false で無効化\x1b[39m\n",
                  name);
  // 赤 LED 点灯。OSTM0 未起動なので ISR は走っておらず、ここで直接 Output する。
  if (g_onboard.enabled) {
    g_sys.ob.ledRedCmd = 1;
    g_onboard.updateOutput(g_sys);
  }
}

static bool initAndReport(IModule& mod, const char* name)
{
  const bool ok = initModule(mod);   // init() を呼び enabled へ反映
  if (!ok) reportInitFailure(name);
  return ok;
}
\end{lstlisting}

報告手段は2系統ある。

\begin{tabularx}{\textwidth}{l X}
\toprule
\textbf{手段} & \textbf{位置づけ} \\
\midrule
シリアル出力（赤字） & 恒久的な記録。どのモジュールが落ちたかがログに残る \\
赤 LED 点灯           & シリアル自体が死んでいる場合の最後の手掛かり \\
\bottomrule
\end{tabularx}

\vspace{2mm}
\texttt{Onboard} と \texttt{Serial} だけは「障害を報告する手段そのもの」なので特別扱いする。
どちらも \texttt{printf} が使えない段階で初期化するため、結果を保持しておき、
シリアル初期化後にまとめて報告する（起動シーケンス \#3--\#5）。
\texttt{Onboard} を先に初期化するのは、\texttt{Serial} が死んでいても
LED で失敗を示せるようにするためである。
全モジュールの初期化後には、失敗が1件でもあれば警告行をまとめて出力する。

\vspace{2mm}
無効化されたモジュールがどこでスキップされるかは
\hyperref[sec:api-moduleinit]{§\ref*{sec:api-moduleinit}} の表を参照。
ISR 配列に載らない \texttt{LineDetector} / \texttt{SDLogger} は
メインループ側が \texttt{enabled} を判定する
(\hyperref[sec:mainloop]{§\ref*{sec:mainloop}})。

\begin{cautionbox}[未確認事項・既知の制約（要実機確認）]
初期化失敗時の挙動は、以下の点がまだ実機で確認できていない。
不具合と断定できる材料は無いが、カメラ未接続などで実際にこの経路を通す前に確認すること。

\begin{itemize}[nosep, leftmargin=*]
  \item \textbf{赤 LED による失敗表示は初期化フェーズの間だけ有効}。
        \texttt{initOSTM0()} 以降は ISR の Logic フェーズ
        (\texttt{applyDrivingPattern()}) が毎周期 \texttt{sys.ob.*LedCmd} を上書きするため、
        点灯は残らない。恒久表示にするには走行ロジック側に障害表示を持たせる必要がある。
        シリアルへの出力は恒久的に残る
  \item \textbf{カメラを無効化したまま走行モードへ入った場合の挙動は未検証}。
        \texttt{sys.line.*} が全て \texttt{false} のままなのでスタートしない見込みだが、
        実機では確認していない
  \item \texttt{g\_serial.printf()} は \texttt{g\_serial.enabled} を見ずに呼ばれ続ける。
        現状 \texttt{Serial::init()} に失敗経路が無いため理論上の話だが、
        将来失敗しうる実装に変えるならこの前提が崩れる
  \item \texttt{Camera::init()} が途中ステップで \texttt{false} を返したときの
        VDC5 の残留状態は未確認（\hyperref[sec:api-camera]{§\ref*{sec:api-camera}}）
\end{itemize}
\end{cautionbox}

\subsection{3フェーズ割り込みハンドラ}\label{sec:isr}

\texttt{generate/inthandler.c} の \texttt{INT\_Excep\_OSTMI0()} から
\texttt{ostm0\_interrupt\_callback()} が呼ばれる。
この関数が実質的なシステムの心臓部である。

\begin{lstlisting}[caption={1ms 割り込みコールバック (mcr\_camera\_2026base.cpp)},label=lst:isr]
void ostm0_interrupt_callback(void)
{
  g_timer_1ms++;    // ModuleTimer の時刻源
  g_cnt_printf++;   // シリアル表示の間隔カウンタ

  // ============ Input フェーズ ============
  // ハードウェア -> SystemData
  for (int i = 0; i < N_IN; ++i) {
    if (s_inputModules[i]->enabled) s_inputModules[i]->updateInput(g_sys);
  }

  // ============ Logic フェーズ ============
  // SystemData -> SystemData
  if (!s_debugMode) {
    applyDrivingPattern(g_sys);
  } else {
    // デバッグモードでも USER_LED は中央2点センサ反応で点灯させる
    g_sys.ob.userLedCmd = (g_sys.line.sensorBin & 0x18) ? 1 : 0;
  }

  // ============ Output フェーズ ============
  // SystemData -> ハードウェア
  for (int i = 0; i < N_OUT; ++i) {
    if (s_outputModules[i]->enabled) s_outputModules[i]->updateOutput(g_sys);
  }
}
\end{lstlisting}

\begin{tabularx}{\textwidth}{l l X}
\toprule
\textbf{配列} & \textbf{登録モジュール} & \textbf{備考} \\
\midrule
\texttt{s\_inputModules[]}  & \texttt{g\_onboard}, \texttt{g\_camera} &
  \texttt{g\_encoder} は現状未登録。\texttt{g\_lineDetector} は処理が重いためメインループ側 \\
\texttt{s\_outputModules[]} & \texttt{g\_motor}, \texttt{g\_servo}, \texttt{g\_onboard} &
  \texttt{g\_sdlogger} はバス制約のためメインループ側。\texttt{g\_serial} は即時出力のため登録不要 \\
\bottomrule
\end{tabularx}

\begin{notebox}[Onboard は両方の配列に登録される]
\texttt{g\_onboard} は Input（SW 読み取り）と Output（LED 反映）の両方を持つため、
2つの配列の両方に登場する。同一インスタンスへのポインタである。
\end{notebox}

\begin{cautionbox}[1ms を超える処理が入る]
XIP 環境では \texttt{Camera::updateInput()} の1ステップが約 8ms かかるため、
実際の割り込み間隔は 1ms を守れず、\texttt{g\_timer\_1ms} は実時間より遅く進む
(\hyperref[sec:xip]{§\ref*{sec:xip}})。
フレーム処理が完了して Vfield 待ちに入る期間にメインループへ CPU 時間が返る構造で
成立させている。時間精度が要求される処理をこの ISR に足さないこと。
\end{cautionbox}

\subsection{メインループと動作モード}\label{sec:mainloop}

起動時のスイッチ状態で2つのモードに分岐する。
判定は \texttt{main()} の早い段階（カメラ初期化前）で行うため、
モード選択の結果をシリアルで確認できる。

\begin{tabularx}{\textwidth}{l l X}
\toprule
\textbf{起動時 SW} & \textbf{モード} & \textbf{ループ関数と動作} \\
\midrule
押されていない & 走行モード     & \texttt{runMainLoop()}。Logic フェーズが有効になり、
  ライン検出・ログ記録・走行終了時の SD 保存を行う \\
押されている   & デバッグモード & \texttt{runDebugLoop()}。Logic フェーズをスキップし、
  カメラ画像を 0/1 のパターンでシリアルへ描画する \\
\bottomrule
\end{tabularx}

\begin{notebox}[ISR 配列外モジュールの enabled 判定はメインループ側にある]
\texttt{g\_lineDetector} と \texttt{g\_sdlogger} は
\texttt{s\_inputModules[]} / \texttt{s\_outputModules[]} に載っていないため、
ISR 側のループによるスキップが効かない。
そこで両モジュールの呼び出しは、以下2つのループのどちらでも
\texttt{if (g\_lineDetector.enabled)} / \texttt{if (g\_sdlogger.enabled)} で囲ってある
(\hyperref[sec:api-moduleinit]{§\ref*{sec:api-moduleinit}})。
\end{notebox}

\subsubsection{走行モード (runMainLoop)}

\begin{enumerate}[nosep, leftmargin=*]
  \item \texttt{sys.cam.frameReady} が立っていれば \texttt{false} に戻し、
        \texttt{g\_lineDetector.updateInput(g\_sys)} を実行する
  \item \texttt{g\_sdlogger.updateOutput(g\_sys)} を毎周期呼ぶ（走行中ログの自動記録）
  \item \texttt{sys.run.finished} が立ったら1回だけモータ・サーボを停止させ、
        \texttt{sys.sd.saveRequested = true} として SD へ書き出す
        （\texttt{g\_sdlogger} が無効なら保存要求そのものを出さない）
  \item \texttt{g\_cnt\_printf} が \texttt{DEBUG\_PRINT\_INTERVAL\_MS}(200) に達したら
        ステータス行（タイマー・フレーム数・パターン・ハンドル・各ラインフラグ・偏差・ログ数）を出力する
\end{enumerate}

\subsubsection{デバッグモード (runDebugLoop)}

\begin{enumerate}[nosep, leftmargin=*]
  \item フレーム完了時に \texttt{g\_lineDetector.updateInput(g\_sys)} を実行する（走行モードと同じ）
  \item 200ms ごとに、閾値 \texttt{DEBUG\_THRESHOLD}(170) で2値化した
        30--100 行（2行飛ばし）を ANSI エスケープ付きで描画する
  \item 偏差が示すライン中心位置を黄色背景でハイライトする
\end{enumerate}

\begin{notebox}[シリアル出力の最適化]
1ピクセルごとに \texttt{printf()} を呼ぶと \texttt{vsnprintf} のオーバーヘッドで
1フレームあたり数千回の書式解析が発生し、描画が極端に遅くなる。
現在の実装は\textbf{1行分を静的バッファ \texttt{lineBuf[]} に組み立ててから
\texttt{print()} で一括送信}する方式に変更済みである。
固定のヘッダ行も \texttt{print()} を使い、書式解析自体を回避している。
\end{notebox}

\section{パラメータ調整ガイド}\label{sec:params}

本章は \texttt{src/core/ProjectConfig.h} の実値を一覧化したものである。
\textbf{走行調整は原則このファイルだけを編集する。}

\begin{cautionbox}[値の正本は ProjectConfig.h]
\texttt{RunLogic.h} や各ドライバヘッダの構造体宣言にはコメントで数値が併記されており、
現在は \texttt{ProjectConfig.h} の実値と一致している。
ただしこれは\textbf{あくまで参考であり、正本は常に \texttt{ProjectConfig.h} 側}である。

過去に片方だけを更新して \texttt{RunLogicConfig} の 31 項目中 23 項目が食い違った実績があるため、
\texttt{ProjectConfig.h} の値を変更したときは\textbf{ヘッダ側のコメントも必ず同時に更新する}こと。
\end{cautionbox}

\section{ベアメタル固有の実装知見}\label{sec:baremetal}

本章は mbed OS が肩代わりしていた処理を自前で用意するにあたって判明した、
このプロジェクト固有の技術的な前提をまとめる。
いずれも\textbf{知らずに触ると起動しなくなる}類のものである。

\subsection{XIP 実行と命令フェッチ制約}\label{sec:xip}

本プロジェクトは SPI フラッシュ（\texttt{0x1800xxxx}）上のコードを
RAM へ展開せずに直接実行する XIP モードで動作する。

SPIBSC（SPI バスコントローラ）のプリフェッチバッファは 32 バイトしかなく、
\textbf{ループの後方分岐でバッファが無効化される}ため、
ループの反復ごとに SPI フラッシュから命令を再フェッチすることになる。
その結果、\texttt{Camera::imageCopy()} の内側ループ（9600 バイトのコピー）だけで
推定 7--8ms を要し、OSTM0 の 1ms 周期を大幅に超過する。

\begin{cautionbox}[割り込み内に重いループを置かない]
1ms 割り込みの中で 1ms を超える処理を行うと、コールバック実行中に次の割り込みが保留され、
コールバック終了と同時に再発火する。CPU が 100\% 割り込み処理に占有され、
メインループが一切実行されなくなる。

現在は \texttt{Camera} のフレーム処理を4ステップに分割し
(\hyperref[sec:api-camera]{§\ref*{sec:api-camera}})、
処理完了後の Vfield 待ち期間にメインループへ CPU 時間を返すことで成立させている。
\end{cautionbox}

\subsection{MMU / L1 キャッシュの有効化}\label{sec:mmu}

\texttt{src/system/system\_init.c} の \texttt{SystemInit()} は
mbed OS の \texttt{system\_RZ\_A1H.c} を移植したもので、\texttt{main()} の冒頭で呼ぶ。

\begin{enumerate}[nosep, leftmargin=*]
  \item \texttt{\_\_FPU\_Enable()} --- VFPv3 有効化（\texttt{FPEXC.EN = 1}）
  \item \texttt{CPG.SYSCR3 = 0x0F} --- SRAM 全バンクの書き込み許可
  \item TLB / 分岐予測配列 / 命令キャッシュの無効化とデータキャッシュの全無効化
  \item \texttt{MMU\_CreateTranslationTable()}（\texttt{mmu\_rzA1H.c}）
  \item \texttt{MMU\_Enable()} --- \texttt{SCTLR.M = 1}, \texttt{SCTLR.AFE = 1}
  \item \texttt{L1C\_EnableCaches()} --- I-cache + D-cache 有効化
  \item \texttt{L1C\_EnableBTAC()} --- 分岐ターゲットアドレスキャッシュ有効化
\end{enumerate}

mbed OS が行っていた \texttt{RZ\_A1\_InitClock()} / \texttt{RZ\_A1\_InitBus()} は
ブートローダーが設定済みのため省略し、
GIC の初期化は \texttt{initGIC()} で別途行う。L2 キャッシュは未使用である。

\begin{cautionbox}[SystemInit() の中でシリアル出力をしないこと]
キャッシュと MMU の切り替え中にペリフェラルへアクセスすると挙動が不定になる。
初期化ログは \texttt{SystemInit()} が戻ってから出力する。
\end{cautionbox}

\begin{notebox}[XIP の制約はキャッシュ有効化後も残っている]
L1 命令キャッシュが有効になれば、原理的には2回目以降のループ反復は
キャッシュから供給されるはずである。
しかし現在も \texttt{Camera} の4ステップ分割が必要な状態であることから、
\hyperref[sec:xip]{§\ref*{sec:xip}} の制約は実効的に解消していないと考えられる。
\textbf{実際の処理時間を実機で計測して見直す余地がある}。
\end{notebox}

\subsection{グローバル C++ コンストラクタの手動実行}\label{sec:ctors}

\texttt{generate/start.S} は \texttt{HardwareSetup()} の後に \texttt{main()} を直接呼び、
\textbf{\texttt{\_\_libc\_init\_array()} を呼ばない}。
一方 GCC 13 はグローバルコンストラクタを \texttt{.init\_array} セクションへ出力するため、
何もしなければ\textbf{グローバル ctor が一切実行されない}。

対策として次の2点を実装している。

\begin{enumerate}[nosep, leftmargin=*]
  \item \texttt{generate/linker\_script.ld} に \texttt{.init\_array} の収集と
        \texttt{\_\_init\_array\_start} / \texttt{\_\_init\_array\_end} ラベルの定義を追加
  \item \texttt{main()} の冒頭で \texttt{runGlobalConstructors()} を呼び、
        両ラベル間のポインタを手動で反復実行
\end{enumerate}

\begin{lstlisting}[caption={グローバルコンストラクタの手動実行},label=lst:ctors]
extern "C" {
  typedef void (*ctor_fn)(void);
  extern ctor_fn __init_array_start[];
  extern ctor_fn __init_array_end[];
}

static void runGlobalConstructors(void)
{
  for (ctor_fn *p = __init_array_start; p < __init_array_end; ++p) {
    (*p)();
  }
}
\end{lstlisting}

\begin{cautionbox}[EMA 化で初めて顕在化した不具合]
EMA 化以前は各ドライバが \texttt{static const} しか使っておらず、
ctor の中身が空でも問題にならなかったため症状が出なかった。
Config 注入で \texttt{\_config} メンバが増えたことにより、
「ctor が走らない $\rightarrow$ \texttt{\_config} が BSS ゼロのまま」となり、
\textbf{Servo の PWM 出力が 0（ペリフェラルのロック）}、
\textbf{LineDetector の全閾値が 0（検出の全崩壊）}といった致命的な不具合になった。

新しいグローバルインスタンスを追加し、内部状態を ctor 初期化リストに置いた時点で
この仕組みに依存することになる点を忘れないこと。
\end{cautionbox}

\subsection{GIC 割り込みディスパッチと VBAR}\label{sec:gic}

\subsubsection{IRQ ディスパッチャの実装}

\texttt{generate/inthandler.c} の \texttt{INT\_Excep\_IRQ()} は生成時点では空関数であり、
そのままでは割り込みが発生してもハンドラが実行されず、
GIC 側の割り込み要求もクリアされない。
Cortex-A9 向けの正しいディスパッチロジックを手動で追加している。

\begin{enumerate}[nosep, leftmargin=*]
  \item \texttt{INTC.ICCIAR} を読んで割り込み要因 ID を取得する
  \item 動的 IRQ ハンドラテーブル \texttt{g\_irq\_handlers[256]} から該当ハンドラを呼ぶ
  \item \texttt{INTC.ICCEOIR} へ書き込んで EOI（End of Interrupt）を通知する
\end{enumerate}

\subsubsection{VBAR の初期化}

Cortex-A9 は「自前の割り込みベクタテーブルがどこにあるか」を
VBAR（Vector Base Address Register）で知る。
未設定だと割り込み発生時にデフォルトの \texttt{0x00000000} 付近（BootROM 等）へ飛んでフリーズする。
\texttt{generate/start.S} に次の1命令を追加して \texttt{vector\_table} のアドレスを登録している。

\begin{center}
\texttt{mcr p15, 0, r0, c12, c0, 0}
\end{center}

\subsubsection{IRQ モードのスタックポインタ}

Cortex-A9 は割り込み時に自動で IRQ モードへ遷移するが、
IRQ モード用の SP が初期化されていないと、
C 言語のハンドラがローカル変数を使った瞬間にクラッシュする。
\texttt{start.S} で 4KB の IRQ 専用スタックを確保している。

\subsubsection{GIC グローバル有効化の順序}

\texttt{initGIC()} は GIC ディストリビュータ（\texttt{ICDDCR}）、
CPU インターフェース（\texttt{ICCICR}）、割り込み優先度マスク（\texttt{ICCPMR}）を有効化し、
\texttt{CPSIE i} で CPU の IRQ を許可する。
これを\textbf{カメラ初期化より前}に実行しなければならない。

\begin{cautionbox}[順序を誤ると割り込みストームでハングする]
カメラ初期化中に VDC5 割り込み（VSYNC / VFIELD, GIC ID 75--97）が
レベルトリガとして GIC に登録されるが、GIC が未有効だと発火しない。
このとき \texttt{WaitVsync(1)} / \texttt{WaitVfield(2)} は割り込みではなく
タイムアウトで抜けている。

その後に GIC を有効化して \texttt{CPSIE i} を実行した瞬間、
蓄積されたレベルトリガ割り込みが一斉に発火する。
VDC5 割り込み（優先度 0x28）は OSTM0（優先度 0x80）より高優先度のため、
OSTM0 を常に横取りし続け、CPU が割り込み処理から抜けられなくなる。

mbed OS ではブートコードが GIC / IRQ を先に有効化しているため、この問題は起きない。
\end{cautionbox}

\subsection{SCIF2 ボーレートのクロックソース}\label{sec:scif}

SCIF のボーレートジェネレータが使うのは P0$\phi$（33.33MHz）ではなく
\textbf{P1$\phi$（66.67MHz）}である。
これを取り違えると実効ボーレートが約2倍ずれて文字化けする。

\begin{align*}
  B &= \frac{P1\phi}{8 \times (\mathtt{SCBRR} + 1)}
     = \frac{66666666}{8 \times 36} = 231481 \approx 230400\ \mathrm{bps} \quad (\text{誤差}\ 0.47\%)
\end{align*}

\begin{tabularx}{\textwidth}{l l X}
\toprule
\textbf{レジスタ} & \textbf{設定値} & \textbf{意味} \\
\midrule
\texttt{SCSMR} & 0x0000 & 8bit データ / ストップ1 / パリティなし \\
\texttt{SCEMR} & 0x0081 & \texttt{BGDM = 1}(bit7), \texttt{ABCS = 1}(bit0) $\rightarrow$ 除算比 8 \\
\texttt{SCBRR} & 35     & mbed の \texttt{DL = (P1CLK + 4*baud) / (8*baud) - 1} と同一 \\
\texttt{SCSCR} & 0x0030 & \texttt{TE = 1}, \texttt{RE = 1}（送受信有効化） \\
\bottomrule
\end{tabularx}

\begin{cautionbox}[STBCR4 は8ビットレジスタ]
SCIF2 のモジュールストップ解除は \texttt{STBCR4} の \textbf{bit 5} である。
かつて \texttt{\textasciitilde(1 << 14)} と書いていた時期があり、
\texttt{uint8\_t} への代入で \texttt{0xFF} に切り詰められた結果、
モジュールストップが解除されないまま SCIF2 のレジスタにアクセスして
バスエラー / データアボートで全動作が停止していた。
mbed の \texttt{MBRZA1H.h} が \texttt{CPG\_STBCR4\_BIT\_MSTP45 = 0x20} と定義しているとおり、
\texttt{\textasciitilde(1 << 5)} が正しい。
\end{cautionbox}

\begin{notebox}[ステータスレジスタは W0C 方式でクリアする]
\texttt{SCFSR} は直接代入（\texttt{= 0x0000}）ではなく、
\texttt{\&= \textasciitilde0x00F3} のように「1 を読んで 0 を書く」方式でクリアすること。
\end{notebox}

\subsection{VDC5 / DVDEC の初期化}\label{sec:vdc5}

\subsubsection{DisplayBase API の採用}

当初は VDC5 / DVDEC をレジスタ直叩きで初期化していたが、
設定値がほぼ 0 のままでカメラが正しく初期化されなかった。
実績のある \texttt{mbed-gr-libs} の \texttt{gr\_peach\_vdc5.c} を取り込み、
高レベル API（\texttt{Graphics\_init}, \texttt{Graphics\_Video\_init},
\texttt{Video\_Write\_Setting}）を呼ぶ方式へ全面的に置き換えている。
これに伴い \texttt{pinmap.h} / \texttt{mbed\_assert.h} 等の
mbed OS 依存ダミーヘッダを \texttt{src/drivers/video/} に追加している。

\subsubsection{LVDS PLL エラー (error = 6) の回避}

LCD を使わずカメラ専用で使う構成では、
\texttt{R\_VDC5\_Initialize} がエラーコード 6（\texttt{VDC5\_ERR\_PARAM\_EXCEED\_RANGE}）を返し、
\texttt{Graphics\_init} が失敗する問題があった。

\textbf{原因:} \texttt{lcd\_type} が \texttt{PARALLEL\_RGB}（非 LVDS）でも
\texttt{panel\_icksel} が \texttt{VDC5\_PANEL\_ICKSEL\_LVDS} のまま残り、
さらに \texttt{lvds\_pll\_calc()} が計算した PLL パラメータ（\texttt{double} 型の \texttt{nfd} 等）を
\texttt{uint16\_t} に変換する際、ベアメタル環境での浮動小数点演算結果が禁止範囲に入り、
LVDS PLL フィードバック分周値（NFD）の範囲チェックに引っかかっていた。

\textbf{対策:} LCD 未使用時は \texttt{panel\_icksel = VDC5\_PANEL\_ICKSEL\_PERI}
（P1 ペリフェラルクロック）を使用し、\texttt{init.lvds = NULL} として
LVDS PLL の初期化自体をスキップする。
カメラの NTSC キャプチャに LVDS PLL は不要で、P1 クロックで十分動作する。

\begin{cautionbox}[\_\_attribute\_\_((interrupt)) による二重リターン]
ARM Cortex-A のコンパイラは \texttt{\_\_attribute\_\_((interrupt))} を付けた関数を、
通常の \texttt{bx lr} ではなく割り込み専用の戻り命令 \texttt{subs pc, lr, \#4} でコンパイルする。

本プロジェクトでは\textbf{最上位の IRQ ハンドラがすでにこの特殊な戻り処理を行っており}、
\texttt{INT\_Excep\_OSTMI0()} 等の個別ハンドラは単なる C 関数として呼ばれる。
それにもかかわらず属性が付いていたため、
普通の C 関数として呼ばれたのに割り込み用の戻り命令を実行してしまい、
PC が不正なアドレスへ飛んでクラッシュしていた。
\end{cautionbox}
